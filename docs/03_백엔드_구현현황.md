# 백엔드 구현 현황 및 미협의 결정사항

> 작성: 2026-09-30 · 브랜치 `feature/backend-setup`
> 기준 문서: `docs/api-spec` 브랜치의 `docs/02_API_명세.md`

API 명세의 엔드포인트 8개를 모두 구현했습니다.
단, **명세에 없어서 팀 협의 없이 임시로 정한 부분**이 있습니다. 아래 [3. 협의 없이 임시로 정한 것](#3-협의-없이-임시로-정한-것-)을 꼭 확인하고, 다르게 가고 싶은 부분이 있으면 말씀해 주세요. 대부분 숫자나 규칙 한 줄만 바꾸면 되도록 만들어 두었습니다.

---

## 1. 실행 방법

```bash
cd backend
npm install
npm start          # http://localhost:3000
```

- 포트 변경: `PORT=4000 npm start`
- 데이터는 **메모리에만** 저장됩니다. 서버를 재시작하면 새로 만든 주문은 사라지고 샘플 데이터 상태로 돌아갑니다.
- 간판 인식을 처음 호출할 때 OCR 언어 데이터(`kor`, `eng`, 약 7MB)를 인터넷에서 자동으로 받습니다. 그래서 첫 요청은 몇 초 걸립니다. 받은 파일(`*.traineddata`)은 `.gitignore`에 등록되어 있습니다.

## 2. 구현 현황

| 기능 | 메서드 | 주소 | 상태 |
|---|---|---|---|
| 가게 목록 조회 | `GET` | `/api/stores` | ✅ 명세대로 |
| 가게 상세 조회 | `GET` | `/api/stores/:id` | ✅ 명세대로 (+ 방문수 증가, 3-5 참고) |
| 간판 인식 | `POST` | `/api/stores/recognize` | ✅ 동작함 (임시 OCR, 3-1 참고) |
| 동네 추천 목록 | `GET` | `/api/stores/recommendations` | ✅ 동작함 (추천 기준 임시, 3-2 참고) |
| 주문/예약 생성 | `POST` | `/api/orders` | ✅ 명세대로 (+ 추가 검증, 3-3 참고) |
| 주문 상태 조회 | `GET` | `/api/orders/:id` | ✅ 명세대로 |
| 가게별 주문 목록 | `GET` | `/api/stores/:id/orders` | ✅ 명세대로 (정렬 기준 3-4 참고) |
| 주문 상태 변경 | `PATCH` | `/api/orders/:id/status` | ✅ 명세대로 (상태 규칙 3-4 참고) |

공통 사항은 다음과 같습니다.
- 모든 에러는 명세대로 `{ "error": "메시지" }` 형태입니다.
- 프론트 개발 서버(Vite 등)에서 바로 호출할 수 있게 **CORS를 전부 허용**해 두었습니다.
- 명세에 없는 주소로 요청하면 `404 { "error": "Not found" }`, 깨진 JSON을 보내면 `400 { "error": "Invalid JSON body" }`가 옵니다.

### 폴더 구조

```
backend/

├── routes/
│   ├── stores.js            # /api/stores/... 주소들
│   └── orders.js            # /api/orders/... 주소들

│   ├── orderService.js      # 주문 생성·검증, 상태 변경 규칙

```

## 3. 협의 없이 임시로 정한 것 ⚠️

### 3-1. 간판 인식 방식

README에는 간판 인식을 `image-proc/`(C / Rust)에서 하기로 되어 있지만, 아직 비어 있습니다. 그래서 **백엔드에서 임시로 동작하게** 만들었습니다.

- 흐름: 사진 업로드 → OCR(`tesseract.js`, 한국어+영어)로 글자 읽기 → 가게 이름·`signKeywords`와 비교 → 매칭된 가게 반환
- 매칭 점수: 가게 이름이 통째로 보이면 +10, `signKeywords` 하나가 보일 때마다 +1. 점수가 높은 순으로 반환합니다.
- **image-proc 연동 시**: `backend/services/signRecognizer.js`의 `extractText(imageBuffer)` 함수 내용만 바꾸면 됩니다. "사진 Buffer를 받아 글자(string)를 돌려준다"는 약속만 지키면 라우트와 매칭 로직은 그대로 둬도 됩니다.
- 업로드 제한은 명세에 숫자가 없어서 임의로 정했습니다.
  - 허용 형식: `jpeg`, `png`, `webp` (그 외는 `400 Unsupported file type`)
  - 최대 용량: **5MB** (넘으면 `413 File too large`)
  - 파일 필드명은 명세대로 `image`입니다. 다른 이름으로 보내면 400입니다.
- 🧪 **명세에 없는 추가 필드**: multipart에 `text` 필드를 같이 보내면 OCR을 건너뛰고 그 글자로 매칭합니다. 카메라나 OCR 없이 프론트 화면을 테스트할 때 쓰려고 만든 **개발용 기능**입니다. 필요 없으면 지워도 됩니다.
  ```bash
  curl -F "image=@사진.png" -F "text=월계 손칼국수" localhost:3000/api/stores/recognize
  ```
- 한계: tesseract는 일반 문서용 OCR이라 기울어지거나 멋을 낸 간판 글씨는 잘 못 읽습니다. 실제 데모 전에 간판 사진으로 테스트가 필요합니다.
- OCR 자체가 실패하면(언어 데이터 다운로드 실패 등) `500 { "error": "Internal server error" }`가 옵니다. 명세에 없는 경우라 일단 이렇게 두었습니다.

### 3-2. 오늘의 동네 추천 기준

명세에는 "신규 가게 또는 저활성 가게 위주"라고만 되어 있어서 숫자를 임의로 정했습니다. 숫자는 `services/storeService.js` 위쪽 상수에서 바꿀 수 있습니다.

| 항목 | 임시값 | 상수 이름 |
|---|---|---|
| 신규 가게 기준 | 등록(`createdAt`) **30일 이내** | `NEW_STORE_DAYS` |
| 저활성 가게 기준 | 방문수(`visits`) **30 이하** | `LOW_VISITS` |
| 좌표를 보냈을 때 반경 | **2km 이내** 가게만 | `RECOMMEND_RADIUS_KM` |
| 최대 개수 | **10개** | `RECOMMEND_LIMIT` |

- 순서: **신규 가게(최근 등록순) → 저활성 가게(방문 적은 순)**
- 두 기준 모두 해당하지 않는 가게(예: 방문 많은 오래된 가게)는 추천에 나오지 않습니다.
- 반경 안에 가게가 없으면 빈 배열 `[]`이 옵니다.

### 3-3. 주문 생성 시 추가 검증

명세의 에러 표에 없는 경우도 막아 두었습니다. 모두 `400`입니다.

| 상황 | 에러 메시지 |
|---|---|
| `storeId`가 정수가 아님 | `Invalid storeId` |
| `items`가 배열이 아니거나 비어 있음 | `items must be a non-empty array` |
| `quantity`가 1 이상 정수가 아님 | `Invalid quantity for menuId: 101` |
| `pickupTime`이 `YYYY-MM-DDTHH:mm` 형식이 아님 | `Invalid pickupTime format (YYYY-MM-DDTHH:mm)` |
| `customerPhone`이 숫자·하이픈 9~13자가 아님 | `Invalid customerPhone format` |

- 검사 순서: 필수값 누락 → 가게 존재(404) → 주문을 받는 가게인지 → 메뉴·수량 → 시간 형식 → 전화번호 형식
- `pickupTime`이 과거 시간인지는 **검사하지 않습니다.** 필요하면 말씀해 주세요.
- 요청에 `totalPrice`를 넣어도 무시하고 서버가 계산합니다 (명세대로).
- `orderType`이 `reservation`인 가게도 주문(`items` 포함)을 받습니다. 명세에서 막는 것은 `none`뿐이라서 이렇게 두었습니다.
- `createdAt`은 **한국 시간(KST)** 기준 `YYYY-MM-DDTHH:mm`입니다.

### 3-4. 주문 상태 변경 규칙

명세의 흐름도(`pending → accepted → done`, `pending → rejected`)를 그대로 규칙으로 만들었습니다.

| 현재 상태 | 바꿀 수 있는 상태 |
|---|---|
| `pending` | `accepted`, `rejected` |
| `accepted` | `done` |
| `rejected`, `done` | 없음 (`409 Order status cannot be changed anymore`) |

명세에 없던 경우는 이렇게 처리합니다.
- `pending → done`처럼 **수락을 건너뛰는 경우**나 `accepted → rejected`처럼 **수락 후 거절하는 경우**는 `409 Cannot change status from pending to done` 형식으로 막습니다.
  - 수락 후 취소가 필요하면 규칙 한 줄(`ALLOWED_TRANSITIONS`)만 바꾸면 됩니다.
- `status`를 안 보내면 `400 status is required`, 이상한 값이면 `400 Invalid status value`가 옵니다.
- 가게별 주문 목록(`GET /api/stores/:id/orders`)은 **픽업 시간이 빠른 순**으로 정렬합니다.

### 3-5. 가게 상세 조회 시 방문수 증가

`visits`를 늘리는 방법이 명세에 없어서, **`GET /api/stores/:id`를 한 번 호출할 때마다 `visits`가 1 올라가게** 했습니다. 추천 기준(저활성 가게)이 실제로 움직이게 하려는 목적입니다.
- 새로고침만 해도 올라가는 단순한 방식입니다. "주문 완료 시 +1" 같은 다른 기준이 좋으면 말씀해 주세요.

### 3-6. 샘플 데이터

- 가게 5개와 주문 3개는 **가상의 데이터**입니다. 주소와 전화번호는 가짜 값이고, 좌표는 월계1동 부근입니다.
- 5번 `신규 오픈 카페`는 `orderType: 'none'`입니다. "주문 안 받는 가게" 화면을 테스트할 때 쓰세요.
- 3번 햇살 미용실 쿠폰은 금액 할인이라 `discountRate: null`입니다. 명세상 `discountRate`는 숫자인데 금액 할인 쿠폰을 어떻게 표현할지 **협의가 필요합니다** (예: `discountAmount` 필드 추가).

## 4. 아직 남은 것 / 협의 필요

- [ ] 간판 인식을 `image-proc`(C/Rust)에서 할지, 지금의 tesseract.js를 계속 쓸지
- [ ] 추천 기준 숫자 (3-2)
- [ ] 수락 후 취소 허용 여부 (3-4)
- [ ] 거절 사유 `rejectionReason` (명세 4장에서도 미정)
- [ ] 금액 할인 쿠폰 표현 방식 (3-6)
- [ ] DB 사용 여부: 지금은 서버를 재시작하면 주문이 사라집니다.
- [ ] 로그인·점주 인증: 프론트 명세에는 있지만 API 명세에 없습니다. 지금은 누구나 아무 가게의 주문을 보고 상태를 바꿀 수 있습니다.
- [ ] API 명세 파일 정리: main의 `docs/02_API명세.md`와 api-spec 브랜치의 `docs/02_API_명세.md`가 따로 있습니다.

## 5. 프론트에서 테스트할 때 참고

```javascript
const BASE = 'http://localhost:3000/api';

// 추천 목록
await fetch(`${BASE}/stores/recommendations?lat=37.62&lng=127.06`).then(r => r.json());

// 간판 인식 (Content-Type은 직접 넣지 말 것 — 브라우저가 boundary까지 알아서 붙임)
const form = new FormData();
form.append('image', file);           // <input type="file"> 또는 카메라 캡처 Blob
// form.append('text', '월계 손칼국수'); // 개발용: OCR 없이 매칭 테스트
await fetch(`${BASE}/stores/recognize`, { method: 'POST', body: form }).then(r => r.json());

// 점주: 주문 수락
await fetch(`${BASE}/orders/1/status`, {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ status: 'accepted' }),
}).then(r => r.json());
```

에러가 났는지는 `res.ok`(또는 `res.status`)로 확인하고, 메시지는 `(await res.json()).error`로 읽으면 됩니다.
