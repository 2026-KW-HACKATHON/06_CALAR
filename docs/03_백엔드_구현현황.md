## 1. 실행 방법

- **Node.js 22.5 이상** 필요 (`node:sqlite` 내장 모듈 사용).

```bash
cd backend
npm install
npm start          # http://localhost:8008
npm test           # 자동 테스트 62개 (약 20초)
```

- 포트 변경: `PORT=4000 npm start`
  - 포트가 이미 사용 중이면 안내 메시지 출력 후 종료됨.
- 데이터는 **SQLite 파일**(`backend/06_calar.sqlite`, `CALAR_DB_PATH`로 변경 가능)에 저장됨. 서버 시작 시 `setup.sql`을 적용하고 샘플 데이터가 없으면 넣음.
- 환경변수는 `backend/.env`에서 읽음. 항목은 `backend/.env.example` 참고 (운영 값 기준, 로컬 개발 값은 파일 하단 주석).
- 서버 시작 시 간판 인식(OCR)을 미리 준비함. `간판 인식(OCR) 준비 완료` 로그 출력 시 준비 완료 상태.
- OCR 언어 데이터(한국어·영어)는 `npm install` 시 npm 패키지(`@tesseract.js-data/*`)로 설치되고, 간판 전처리는 저장소에 포함된 `image-proc/pkg/calar_imgproc.wasm`을 사용함. **서버 실행 중 인터넷 불필요, Rust 설치 불필요.**
- 실제 간판 사진 인식률 확인: `npm run evaluate:signs -- <사진 폴더>` (사용법은 `image-proc/README.md` 5장)

## 3. 협의 없이 임시로 정한 것 ⚠️

### 3-1. 간판 인식 방식

- README상 간판 인식은 `image-proc/`(C / Rust) 담당이었으나 비어 있었음.
- **결정: image-proc은 Rust로 작성한 사진 전처리 모듈로 구현하고, 글자 인식(OCR)은 tesseract.js를 유지함.**
  - OCR 엔진 자체를 새로 만드는 것은 해커톤 기간에 비현실적이라고 판단함.
  - 대신 실제 휴대폰 사진에서 OCR이 실패하는 원인(회전, 그림자, 잡음, 색 대비, 큰 사진)을 image-proc이 해결함.
  - WebAssembly로 빌드한 파일을 저장소에 포함해 Windows 개발 환경·Ubuntu 서버 모두 컴파일러 없이 동작함.
  - 처리 단계·측정 결과·빌드 방법은 `image-proc/README.md` 참고.

**흐름**
1. 사진 업로드.
2. 파일 내용으로 실제 이미지 여부 및 해상도 검사.
3. OCR 전용 자식 프로세스에서 image-proc 전처리 → 흑백(gray)·이진(binary) 이미지 생성.
4. tesseract.js(한국어+영어)로 최대 4가지 방식으로 읽음. **읽을 때마다 가게 매칭을 확인해 매칭되면 멈춤.**
5. 인식된 글자를 가게 이름·`signKeywords`와 비교해 매칭된 가게 반환.
- image-proc을 쓸 수 없으면(wasm 파일 없음, 디코딩 실패) 원본 사진을 예전 방식(이진화 2종)으로 읽음.

**인식 정확도 (합성 사진 측정, `image-proc/README.md` 3장)**

| 사진 세트 | 기존(원본 + 이진화 2종) | 현재(image-proc + 조기 종료) |
|---|---|---|
| 원본 간판 9장 | 9/9, 평균 1.0초 | 9/9, 평균 1.2초 |
| 검증용 합성 사진 54장 (튜닝에 사용 안 함) | 20/54, 평균 16.6초, 30초 초과 19건 | 51/54, 평균 1.4초, 최대 3.6초 |

- 다른 가게 간판의 오인식은 두 방식 모두 0건.
- ⚠️ 합성 사진(원본 간판을 원근 왜곡·그림자·흐림·EXIF 회전 등으로 망가뜨린 것) 기준임. **실제 휴대폰 사진으로는 미검증.** 데모 전 `npm run evaluate:signs`로 확인 필요한 것으로 판단됨.
- 기존 방식의 적응형 이진화는 잡음 많은 사진에서 10~20초 이상 걸려 30초 제한(504)에 자주 걸렸음. 운영 중이던 방식의 문제였으므로 이번 변경으로 함께 해결됨.

**매칭 규칙** (변경 없음)
- **가게 이름 전체가 보이거나 키워드 2개 이상 일치** 시에만 해당 가게로 인정.
  - "월계부동산", "스타벅스 카페", "엄마손칼국수" 같은 다른 가게 간판은 매칭되지 않음.
- 다른 키워드에 포함되는 키워드('손칼국수' 안의 '칼국수')는 별도 점수 없음.
- 띄어쓰기, 특수문자(`·`, `!`), 줄바꿈은 무시하고 비교함.
- 결과는 점수 높은 순. 첫 번째 항목이 가장 유력한 후보임.

**업로드 제한** (명세에 수치가 없어 임의로 정함)

| 상황 | 응답 |
|---|---|
| 이미지 파일 누락 | `400 Image file is required` |
| jpeg/png/webp가 아님 (**파일 내용으로 판단**. 이름·형식 위조도 걸러짐, 아이폰 HEIC도 해당) | `400 Unsupported file type` |
| 헤더는 정상이나 내용이 깨진 이미지 | `400 Invalid image file` |
| `image` 필드가 아니거나 파일 2개 이상 | `400 Send exactly one image file in the 'image' field` |
| 10MB 초과 | `413 File too large` |
| 해상도 5천만 화소 초과 (파일은 작아도 메모리를 폭증시키는 이미지 방지) | `413 Image dimensions too large` |
| 인식 요청이 동시에 5개 초과 | `503 Sign recognition is busy, please try again` |
| OCR 준비 실패 | `503 Sign recognition is temporarily unavailable` |
| 인식 30초 초과 (전처리 + 모든 읽기 합계) | `504 Sign recognition timed out` |
| 인식 중 OCR 프로세스 비정상 종료 | `500 Sign recognition failed` |

→ **프론트는 200이 아닌 응답 수신 시 전부 "수동 검색으로 전환" 안내를 표시하면 됨.**

**안정성**
- 전처리와 OCR은 별도 프로세스에서 실행함.
  - tesseract.js에는 깨진 이미지 하나로 서버 전체가 종료되거나, 언어 데이터 로딩 실패 시 무한 대기하는 문제가 있음.
  - 별도 프로세스이므로 메인 서버는 영향 없음.
- 문제가 발생한 OCR 프로세스는 강제 종료 후 다음 요청 시 재실행됨.
- image-proc wasm은 외부 함수 호출이 없는 순수 계산 모듈이며, 큰 사진 처리로 메모리가 커지면(256MB 초과) 인스턴스를 새로 만듦.

**🧪 명세에 없는 추가 필드: `text`**
- multipart에 `text` 필드를 함께 보내면 OCR을 생략하고 해당 글자로 매칭함.
- 카메라나 OCR 없이 프론트 화면을 테스트하기 위한 **개발용 기능**임. 불필요 시 삭제 가능.
```bash
curl -F "image=@사진.png" -F "text=월계 손칼국수" localhost:8008/api/stores/recognize
```

### 3-2. 오늘의 동네 추천 기준

- 명세에는 "신규 가게 또는 저활성 가게 위주"로만 기재되어 있어 수치를 임의로 정함.
- 수치는 `services/storeService.js` 상단 상수에서 변경 가능.

| 항목 | 임시값 | 상수 이름 |
|---|---|---|
| 신규 가게 기준 | 등록(`createdAt`) **30일 이내** | `NEW_STORE_DAYS` |
| 저활성 가게 기준 | 방문수(`visits`) **30 이하** | `LOW_VISITS` |
| 좌표 전송 시 반경 | **2km 이내** 가게만 | `RECOMMEND_RADIUS_KM` |
| 최대 개수 | **10개** | `RECOMMEND_LIMIT` |

- 순서: **신규 가게(최근 등록순) → 저활성 가게(방문 적은 순)**
- 두 기준 모두 해당하지 않는 가게(방문 많은 오래된 가게)는 추천에서 제외됨.
- 반경 내 가게가 없으면 빈 배열 `[]` 반환.
- 각 가게에 추천 이유 `reason`을 포함함 (이슈 #3 프론트 요청 반영). 문구는 `storeService.js` 상단 상수에서 변경 가능.

| 구분 | `reason` | 상수 이름 |
|---|---|---|
| 신규 가게 | `새로 오픈했어요` | `REASON_NEW` |
| 저활성 가게 | `숨어있는 동네 가게예요` | `REASON_LOW_VISITS` |

  - 프론트 제안 문구는 "숨어있던 동네 맛집이에요"였으나 세탁소·미용실도 추천되므로 업종 중립적인 문구로 정함.
- 좌표가 없는 가게(점주 화면에서 등록한 가게는 좌표 입력란이 없음)는 거리를 알 수 없으므로 **반경 필터에서 빼지 않음.**
  - 이전에는 좌표 없음을 (0, 0)으로 계산해 위치를 보낸 사용자에게 신규 가게가 전부 사라졌음.

### 3-3. 주문 생성 시 추가 검증

- 명세의 에러 표에 없는 경우도 차단함. 모두 `400`.

| 상황 | 에러 메시지 |
|---|---|
| body가 JSON 객체가 아님 (배열, 빈 body, form 형식 등) | `Request body must be a JSON object` |
| `storeId`가 1 이상의 정수가 아님 (`"1"` 같은 문자열 포함) | `Invalid storeId` |
| `items`가 배열이 아니거나 비어 있음 | `items must be a non-empty array` |
| `items` 항목이 객체가 아님 | `Each item must be an object with menuId and quantity` |
| `quantity`가 1 이상 정수가 아님 | `Invalid quantity for menuId: 101` |
| 메뉴 하나의 수량 99 초과 | `Quantity for menuId: 101 exceeds 99` |
| `pickupTime` 형식 오류 또는 존재하지 않는 날짜 (2월 30일, 24:00 등) | `Invalid pickupTime format (YYYY-MM-DDTHH:mm)` |
| `pickupTime`이 과거 (현재 분까지는 허용) | `pickupTime must not be in the past` |
| `pickupTime`이 30일 이후 | `pickupTime must be within 30 days` |
| `pickupTime`이 가게 영업시간 외 | `pickupTime is outside business hours` |
| 전화번호 형식 오류 | `Invalid customerPhone format` |

- 허용 전화번호: `010-1234-5678`, `01012345678`, `02-123-4567`, `031-123-4567` 등. 국제번호(`+82`)와 띄어쓰기는 불가.
- **동일 메뉴가 여러 번 오면 하나로 합산함.** 예: 101번 2개 + 101번 1개 → 101번 3개
- 요청에 `totalPrice`, `status`, `id` 포함 시 무시하고 서버가 결정함 (명세대로).
- `orderType`이 `reservation`인 가게도 주문(`items` 포함) 접수함. 명세상 차단 대상은 `none`뿐이기 때문임.
- 모든 시간은 **한국 시간(KST)** 기준. `createdAt`은 `YYYY-MM-DDTHH:mm` 형식.
- JSON body 100KB 초과 시 `413 Request body too large` 반환.
- 크레딧 선결제(`paymentMethod: "credit"`)는 `requestId`(UUID)로 중복 결제를 막음. 같은 `requestId` 재요청은 기존 주문을 돌려주며, 비교는 같은 메뉴를 합친 뒤의 항목 기준임 (같은 메뉴를 나눠 보낸 주문의 재시도가 409로 잘못 거부되던 문제 수정).

### 3-4. 주문 상태 변경 규칙

- 명세의 흐름도(`pending → accepted → done`, `pending → rejected`)를 그대로 규칙화함.

| 현재 상태 | 변경 가능한 상태 |
|---|---|
| `pending` | `accepted`, `rejected` |
| `accepted` | `done` |
| `rejected`, `done` | 없음 (`409 Order status cannot be changed anymore`) |

명세에 없던 경우의 처리
- `pending → done`(수락 생략), `accepted → rejected`(수락 후 거절), 동일 상태로 변경 → `409 Cannot change status from pending to done` 형식.
  - 수락 후 취소 허용 시 규칙 한 줄(`ALLOWED_TRANSITIONS`)만 수정하면 됨.
- `status` 누락 시 `400 status is required`, 잘못된 값이면 `400 Invalid status value`.
- 가게별 주문 목록은 **픽업 시간 빠른 순**, 동일하면 먼저 들어온 순으로 정렬함.

### 3-5. 방문수(`visits`) 집계

- 명세에 `visits` 증가 방법이 없어, **가게 상세 조회(`GET /api/stores/:id`) 시 방문 1회로 집계**함.
- 동일 사용자(IP + 브라우저 정보)가 동일 가게를 **30분 내 재조회 시 미집계.** 새로고침이나 React StrictMode 중복 호출로 인한 수치 부풀림 방지 목적임.
- 한계: 같은 와이파이에서 같은 기종·브라우저 사용자는 한 명으로 집계될 수 있음.
- "주문 완료 시 +1" 등 다른 기준 채택 여부는 협의 필요.

### 3-6. 샘플 데이터

- 가게 5개, 주문 3개는 **가상 데이터**임. 주소·전화번호는 가짜 값이며 좌표는 월계1동 부근.
- 5번 `모퉁이 카페`는 `orderType: 'none'`. "주문 불가 가게" 화면 테스트용.
  - 명세 예시의 "신규 오픈 카페"는 흔한 단어로만 구성된 이름이라 간판 오탐 방지를 위해 변경함.
- **`signKeywords` 작성 규칙**: 간판에 실제 쓰인 단어를 넣되, '월계'(동네 이름), '카페'(업종) 같은 흔한 단어는 최대 1개만 포함. 흔한 단어 2개 포함 시 다른 가게 간판에도 매칭됨. (`data/stores.js` 상단 주석 참고)
- 3번 햇살 미용실 쿠폰은 금액 할인이라 `discountRate: null`임. 쿠폰 등록 시 `discountRate` 생략 또는 `null`을 허용함 (생략 시 400이던 문제 수정). 다만 할인 금액 필드는 없어 금액은 제목에만 적혀 있음 → 금액 할인 쿠폰 표현 방식(`discountAmount` 필드 추가 등)은 **협의 필요.**
  - 프론트 `CouponCard`는 현재 `discountRate`가 `null`이면 `null% 할인`으로 표시함 (프론트 수정 필요).
- 쿠폰의 사용 기간(`validFrom`~`validUntil`)이 있으면 그 기간에만 고객 화면에 노출함 (기간이 지난 쿠폰이 계속 보이던 문제 수정).

### 3-7. 공통 입력 규칙

| 입력 | 규칙 |
|---|---|
| 주소의 `:id` | 1 이상의 정수만 허용. `abc`, `1.0`, `0x1`, `01`은 **존재하지 않는 대상(404)**으로 처리 |
| `lat`, `lng` | 둘 다 필수. 숫자(소수점 허용)이며 위도 ±90, 경도 ±180 이내. 위반 시 400 |
| 쿼리 값 (`category`, `keyword`, `status`) | 앞뒤 공백 무시. 빈 값은 미전송으로 처리. 동일 키 중복 전송 시 400 |
| `keyword` 검색 | 띄어쓰기·특수문자 무시 (`손 칼국수` → `월계 손칼국수` 검색됨) |
| `%` 인코딩이 깨진 주소 | 400 |

### 3-8. 요청 제한 (문자 인증·복구)

- 계정 관련 공개 주소는 IP별 15분 단위로 요청 수를 제한함. 수치는 `routes/auth.js`에서 변경 가능.

| 대상 | 한도 | 이유 |
|---|---|---|
| 문자 인증번호 발송 | 30회 | 문자 발송 비용 보호. 같은 번호 재발송은 60초 간격 제한이 별도로 있음 |
| 문자 인증번호 확인 | **틀린 시도만** 20회 | 요청 1건당 5회 제한이 별도로 있음 |
| 이메일 인증·비밀번호 복구 | 10회 (4개 주소 합산) | 기존 값 유지 |

- 이전에는 위 전부를 IP당 10회로 함께 셌음. 문자 인증은 고객의 유일한 로그인 수단이고 로그인 1회에 2번 요청하므로, **같은 와이파이(가게, 행사장, 데모 현장)에서 6번째 고객부터 429로 로그인 불가**였음.

### 3-9. 관리자 계정

- 서버 시작 시 `CALAR_ADMIN_EMAIL`/`CALAR_ADMIN_PASSWORD`가 있으면 계정이 **없을 때만** 관리자 계정을 생성함.
- 같은 이메일의 일반 계정이 이미 있으면 서버 시작 시 승격하지 않고 경고만 출력함.
  - 이전에는 자동 승격했음. 공개 가입 API로 누군가 관리자 이메일을 먼저 가입해 두면, 다음 재시작 때 **그 사람이 정한 비밀번호로 관리자 로그인이 가능**했음 (보안 문제, 테스트로 재현 후 수정).
  - 승격이 필요하면 서버 콘솔에서 `npm run admin:provision` 실행 (비밀번호를 지정한 값으로 바꾸고 기존 세션을 끊음).
- 관리자는 자기 계정을 정지하거나 관리자 권한을 해제할 수 없음. `isActive`는 `true`/`false`/`0`/`1`만 허용함 (`null`, `"0"` 등으로 자기 계정을 정지시키던 우회 차단).

## 5. 프론트 호출 시 참고

```javascript
const BASE = '/api'; // 개발 서버(Vite)가 8008 포트로 프록시함. 로그인이 필요한 주소는 Authorization: Bearer <token> 헤더 필요

// 추천 목록
await fetch(`${BASE}/stores/recommendations?lat=37.62&lng=127.06`).then(r => r.json());

// 간판 인식 (Content-Type 직접 지정 금지 — 브라우저가 boundary까지 자동 설정)
const form = new FormData();
form.append('image', file);            // <input type="file" accept="image/*" capture> 또는 카메라 캡처 Blob
// form.append('text', '월계 손칼국수');  // 개발용: OCR 없이 매칭 테스트
const res = await fetch(`${BASE}/stores/recognize`, { method: 'POST', body: form });
if (!res.ok) {
  // 400/413/5xx 전부 → "수동 검색으로 전환하시겠어요?" 안내
}
const { matched, stores } = await res.json();  // matched가 false여도 수동 검색 안내
// 추천 카드: store.reason 을 그대로 표시 ("새로 오픈했어요" 등)

// 점주: 주문 수락 (점주 로그인 토큰 필요)
await fetch(`${BASE}/owner/orders/1/status`, {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
  body: JSON.stringify({ status: 'accepted' }),
}).then(r => r.json());
```

- 에러 여부는 `res.ok`(또는 `res.status`)로 확인하고, 메시지는 `(await res.json()).error`로 확인함.
- `storeId`, `menuId`, `quantity`는 **숫자**로 전송해야 함. `useParams()`로 받은 id는 문자열이므로 `Number(id)` 변환 필요.
